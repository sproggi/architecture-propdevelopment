# Требования к внешним интеграциям для сервисов "Умный дом"

## 1. Требования к безопасности

### 1.1 Транспортная безопасность

| № | Требование | Обоснование | Приоритет |
|---|------------|-------------|-----------|
| 1.1 | **Взаимная аутентификация (mTLS)** | Обеспечивает идентификацию обеих сторон (PropDevelopment и партнёр) на транспортном уровне. Предотвращает MitM-атаки и подмену сторон. | Критический |
| 1.2 | **Использование TLS 1.3** | Защита ПДн, биометрических данных и данных об автомобилях от перехвата. TLS 1.3 обеспечивает современные криптографические алгоритмы и исключает устаревшие протоколы. | Критический |
| 1.3 | **Шифрование данных при передаче** | Все данные, передаваемые между системами, должны быть зашифрованы с использованием современных алгоритмов (AES-256). | Критический |
| 1.4 | **Регулярная ротация сертификатов** | Автоматическое обновление TLS-сертификатов не реже 1 раза в 90 дней для предотвращения истечения срока действия. | Высокий |

### 1.2 Аутентификация и авторизация

| № | Требование | Обоснование | Приоритет |
|---|------------|-------------|-----------|
| 1.5 | **OAuth 2.0 + Client Credentials Grant** | Партнёр получает access token от сервиса аутентификации PropDevelopment, используя client_id и client_secret. Токен должен иметь ограниченный срок действия (не более 1 часа). | Критический |
| 1.6 | **API Key для каждого запроса** | Дополнительный слой защиты — каждый запрос содержит уникальный API Key, который проверяется на API Gateway. | Критический |
| 1.7 | **Ограничение доступа на основе Scopes** | Определение набора разрешённых действий через OAuth 2.0 Scopes: `smart-home:read`, `smart-home:write`, `smart-home:admin`. | Высокий |
| 1.8 | **Подпись запросов (HMAC-SHA256)** | Обеспечение целостности и подлинности запросов на уровне приложения. Каждый запрос должен содержать подпись, сгенерированную с использованием секретного ключа. | Высокий |
| 1.9 | **Проверка JWT токена** | Проверка подписи, срока действия и прав (claims) в каждом запросе к микросервисам. | Критический |

### 1.3 Контроль доступа и изоляция

| № | Требование | Обоснование | Приоритет |
|---|------------|-------------|-----------|
| 1.10 | **Многопользовательская изоляция (Multitenancy)** | Строгое разделение данных по управляющим компаниям — партнёр из одной УК не должен видеть данные другой УК. Каждый запрос должен содержать идентификатор УК (`tenant_id`). | Критический |
| 1.11 | **RBAC (Role-Based Access Control)** | Назначение ролей для каждого партнёра. Доступные роли: «Партнёр-УК», «Партнёр-Интегратор». | Высокий |
| 1.12 | **ABAC (Attribute-Based Access Control)** | Дополнительная фильтрация на основе атрибутов (тип устройства, временные ограничения, геозона). | Средний |
| 1.13 | **Принцип минимальных привилегий** | Партнёр должен иметь доступ только к тем данным и функциям, которые необходимы для выполнения его задач. | Критический |

### 1.4 Защита от атак

| № | Требование | Обоснование | Приоритет |
|---|------------|-------------|-----------|
| 1.14 | **Rate Limiting (ограничение частоты запросов)** | Защита от DDoS-атак и злоупотреблений. Лимит: 1000 запросов в минуту на один API Key. | Высокий |
| 1.15 | **Валидация входных данных** | Предотвращение SQL-инъекций, XSS-атак и других инъекционных атак через входные данные от внешней системы. Использовать allowlist-валидацию. | Критический |
| 1.16 | **Защита от replay-атак** | Использование уникальных идентификаторов запросов (`X-Request-Id`) и временных меток с проверкой допустимого временного окна (не более 5 минут). | Высокий |
| 1.17 | **Защита от перебора (Brute Force)** | Блокировка API Key после 5 неудачных попыток аутентификации на 15 минут. | Высокий |

### 1.5 Аудит и логирование

| № | Требование | Обоснование | Приоритет |
|---|------------|-------------|-----------|
| 1.18 | **Аудит всех запросов и ответов** | Ведение журнала всех взаимодействий с внешней платформой для расследования инцидентов. Журнал должен содержать: timestamp, метод, URL, IP-адрес, `tenant_id`, результат. | Критический |
| 1.19 | **Маскирование чувствительных данных в логах** | В логах не должны отображаться ПДн, биометрические данные и номера автомобилей в открытом виде. Использовать маскировку или хеширование. | Высокий |
| 1.20 | **Централизованное хранение логов** | Все логи должны храниться в SIEM-системе с возможностью поиска и корреляции событий в режиме реального времени. | Высокий |
| 1.21 | **Срок хранения логов** | Логи аудита должны храниться не менее 1 года для соответствия требованиям законодательства РФ. | Высокий |

### 1.6 Безопасность данных

| № | Требование | Обоснование | Приоритет |
|---|------------|-------------|-----------|
| 1.22 | **Классификация данных** | Все данные, передаваемые в рамках интеграции, должны быть классифицированы по уровням чувствительности (ПДн, биометрия, номера автомобилей). | Критический |
| 1.23 | **Хранение биометрических данных** | Биометрические данные не должны передаваться в PropDevelopment. Платформа должна хранить только хеш-образы лиц. | Критический |
| 1.24 | **Шифрование данных в покое** | Все данные, хранящиеся в `smart-home-integration-db`, должны быть зашифрованы на уровне базы данных или файловой системы. | Высокий |
| 1.25 | **Управление ключами шифрования** | Реализовать централизованное управление ключами шифрования с использованием HSM (Hardware Security Module). Ключи должны храниться отдельно от данных. | Критический |
| 1.26 | **Обезличивание данных для аналитики** | При передаче данных в DWH для BI-отчётности ПДн должны быть обезличены или псевдонимизированы. | Высокий |

## 2. Протоколы аутентификации и авторизации

### 2.1 Уровни аутентификации

| Уровень | Протокол/Технология | Описание |
|---------|--------------------|----------|
| Транспортный | **mTLS (mutual TLS)** | Взаимная сертификатная аутентификация. PropDevelopment и партнёр обмениваются сертификатами, подписанными доверенными ЦС. |
| Уровень приложений | **OAuth 2.0 + Client Credentials Grant** | Партнёр получает access token от сервиса аутентификации PropDevelopment (`auth-service-1`), используя client_id и client_secret. |
| Дополнительный | **API Key** | Дополнительный слой защиты — каждый запрос содержит API Key, который проверяется на API Gateway. |

### 2.2 Уровни авторизации

| Протокол/Технология | Описание |
|--------------------|----------|
| **OAuth 2.0 Scopes** | Определяют набор разрешённых действий. Например: `smart-home:read` — чтение статуса устройств; `smart-home:write` — управление устройствами; `smart-home:admin` — управление конфигурацией. |
| **RBAC (Role-Based Access Control)** | Назначение ролей для каждого партнёра. Например: «Партнёр-УК» — доступ только к данным своей УК; «Партнёр-Интегратор» — технический доступ к API. |
| **ABAC (Attribute-Based Access Control)** | Дополнительная фильтрация на основе атрибутов (например, УК ID, тип устройства, временные ограничения). |
| **JWT (JSON Web Tokens)** | Токены содержат информацию о правах доступа (claims), что позволяет микросервисам принимать решения об авторизации без обращения к центральному сервису. |

### 2.3 Порядок аутентификации и авторизации

| Шаг | Действие | Участник | Протокол |
|-----|---------|----------|----------|
| 1 | Проверка транспортного уровня (mTLS) | API Gateway → Платформа | mTLS |
| 2 | Проверка API Key | API Gateway → Платформа | API Key |
| 3 | Проверка Rate Limiting | API Gateway → Платформа | - |
| 4 | Запрос на получение JWT токена | API Gateway → auth-service-1 | OAuth 2.0 |
| 5 | Проверка client_id и client_secret | auth-service-1 → API Gateway | OAuth 2.0 |
| 6 | Выпуск JWT токена с Scopes | auth-service-1 → API Gateway | OAuth 2.0 |
| 7 | Проверка JWT токена (подпись, срок, scopes) | smart-home-integration-service | JWT |
| 8 | Проверка RBAC (роль партнёра) | smart-home-integration-service | RBAC |
| 9 | Проверка ABAC (атрибуты, tenant_id) | smart-home-integration-service | ABAC |
| 10 | Проверка прав на уровне записей (Row-Level Security) | tenant-core-app / CRM | RLS |

## 3. Организация взаимодействия между системами

### 3.1 Общие требования к взаимодействию

| № | Требование | Описание |
|---|------------|----------|
| 3.1 | **RESTful API** | Использовать RESTful архитектуру с понятными ресурсами и HTTP-методами (GET, POST, PUT, DELETE). |
| 3.2 | **Версионирование API** | Использовать версионирование в URL (например, `/api/v1/`). Изменения, ломающие обратную совместимость, должны выпускаться в новой версии. |
| 3.3 | **OpenAPI 3.0 (Swagger)** | Предоставить документацию API в формате OpenAPI 3.0 для автоматической генерации клиентов и тестирования. |
| 3.4 | **Корректные HTTP-статусы** | Использовать стандартные HTTP-статус-коды (200, 400, 401, 403, 404, 429, 500). |
| 3.5 | **Пагинация** | Для методов, возвращающих списки, реализовать пагинацию с параметрами `page`, `size`, `sort`. |
| 3.6 | **Фильтрация** | Реализовать фильтрацию по параметрам с использованием query-параметров. |
| 3.7 | **Максимальный размер запроса** | Ограничить размер тела запроса до 1 МБ для предотвращения DoS-атак. |
| 3.8 | **Таймауты** | Установить таймауты для внешних вызовов: 30 секунд для чтения, 60 секунд для записи. |
| 3.9 | **Retry-политика** | Реализовать повторные попытки (retry) с экспоненциальной задержкой для временных сбоев (максимум 3 попытки). |
| 3.10 | **Circuit Breaker** | Внедрить паттерн Circuit Breaker для защиты от каскадных отказов при недоступности внешней платформы. |

### 3.2 Требования к форматам данных

| № | Требование | Описание |
|---|------------|----------|
| 3.11 | **Формат данных** | Использовать JSON для всех запросов и ответов. Content-Type: application/json. |
| 3.12 | **Кодировка** | Использовать UTF-8 для всех текстовых данных. |
| 3.13 | **Формат даты и времени** | Использовать ISO 8601 (YYYY-MM-DDTHH:mm:ssZ). |
| 3.14 | **Уникальные идентификаторы** | Каждый запрос должен содержать уникальный идентификатор (`X-Request-Id`) для трассировки. |
| 3.15 | **Подпись запросов** | Каждый запрос должен содержать подпись, сгенерированную с использованием HMAC-SHA256 и секретного ключа. |
| 3.16 | **Подпись ответов** | Каждый ответ должен содержать подпись, сгенерированную с использованием HMAC-SHA256 и секретного ключа. |

### 3.3 Сценарии взаимодействия

#### Сценарий 1: Открытие двери через интеллектуальный домофон

| Шаг | Действие | Участник | Протокол | Безопасность |
|-----|---------|----------|----------|--------------|
| 1 | Собственник подходит к домофону | Домофон (Партнёр) | - | - |
| 2 | Домофон делает запрос на распознавание лица | Платформа "Умный дом" | Внутренний | - |
| 3 | Распознавание выполнено | Платформа "Умный дом" | - | - |
| 4 | Платформа отправляет запрос на проверку прав доступа | → API Gateway (PropDevelopment) | HTTPS REST + mTLS | Аутентификация партнёра |
| 5 | API Gateway проверяет сертификат и передаёт запрос | API Gateway | - | mTLS, Rate Limiting |
| 6 | Запрос направляется в `smart-home-integration-service` | API Gateway → smart-home-integration-service | HTTPS REST | - |
| 7 | Сервис проверяет JWT токен, извлекает `tenant_id` (УК) | smart-home-integration-service | - | Проверка JWT, RBAC |
| 8 | Сервис запрашивает права доступа у `crm-tenant-db` | smart-home-integration-service → CRM | JDBC | Проверка Row-Level Security |
| 9 | Проверка: есть ли у собственника доступ? | CRM | - | - |
| 10 | Возврат результата (да/нет) | CRM → smart-home-integration-service | JDBC | - |
| 11 | Сервис возвращает ответ Платформе | smart-home-integration-service → Платформа | HTTPS REST + mTLS | Подпись ответа (HMAC) |
| 12 | Платформа выполняет действие (открытие двери) | Платформа "Умный дом" | - | - |

#### Сценарий 2: Включение/отключение сервиса Умного дома собственником

| Шаг | Действие | Участник | Протокол | Безопасность |
|-----|---------|----------|----------|--------------|
| 1 | Собственник открывает мобильное приложение | Витрина (Mobile App) | - | Аутентификация через Keycloak |
| 2 | Переходит в раздел "Умный дом" | Mobile App | - | - |
| 3 | Включает/отключает опцию (домофон или шлагбаум) | Mobile App | - | - |
| 4 | Запрос отправляется в `tenant-core-app` | Mobile App → tenant-core-app | HTTPS REST | Проверка JWT |
| 5 | `tenant-core-app` проверяет права собственника | tenant-core-app → CRM | REST | Проверка RBAC |
| 6 | CRM обновляет настройки в `crm-tenant-db` | CRM → crm-tenant-db | JDBC | - |
| 7 | CRM возвращает успешный ответ | CRM → tenant-core-app | REST | - |
| 8 | `tenant-core-app` отправляет запрос на синхронизацию прав доступа в `smart-home-integration-service` | tenant-core-app → smart-home-integration-service | REST | Сервис-сервисная аутентификация (JWT) |
| 9 | `smart-home-integration-service` отправляет обновление в Платформу | smart-home-integration-service → Платформа | HTTPS REST + mTLS | mTLS, подпись запроса |
| 10 | Платформа обновляет права доступа | Платформа "Умный дом" | - | - |
| 11 | Ответ возвращается в мобильное приложение | tenant-core-app → Mobile App | HTTPS REST | - |

### 3.4 Форматы данных для интеграции

#### Запрос на проверку доступа (от Платформы к PropDevelopment)

**Endpoint:** `POST /api/v1/smart-home/access/check`

**Заголовки:**

| Заголовок | Значение | Описание |
|-----------|----------|----------|
| Authorization | Bearer `<JWT_TOKEN>` | JWT токен, полученный от auth-service-1 |
| X-API-Key | `<API_KEY>` | Уникальный API Key партнёра |
| X-Request-Id | `<UUID>` | Уникальный идентификатор запроса |
| X-Timestamp | `2026-09-05T10:00:00Z` | Временная метка запроса |
| Content-Type | `application/json` | Формат данных |

**Тело запроса:**

```json
{
  "tenant_id": "uk-12345",
  "device_type": "intercom",
  "device_id": "intercom-001",
  "user_identifier": "face-hash-abc123",
  "timestamp": "2026-09-05T10:00:00Z",
  "signature": "hmac-sha256-signature"
}
```
